## Advertisement used by the Android app

- A connectable legacy advertisement lists the 16-bit service UUID `FC82` (`82 FC` in the UUID list on air). The corresponding Android UUID is `0000fc82-0000-1000-8000-00805f9b34fb`.
- The manufacturer-specific AD field is `06 FF 4A 09 09 42 42` including its length and type. Android inserts the company ID `0x094A` in little-endian order. The app passes only `09 42 42` as the data. The final two bytes are the exact literal used by Zwahoo. The Ride capture describes this field as a short BLE address. Whether Zwift checks that field against the transmitter address is unknown. [Zwahoo advertising code](https://github.com/jespern/zwahoo/blob/93a558e36fe72421d86a43991362c5ead48a4d2c/zwahoo.ino#L426-L451) · [Makinolo's Ride capture and interpretation](https://www.makinolo.com/blog/2024/07/26/zwift-ride-protocol/)
- The optional scan-response name is `Zwift SF2`. Android takes the name from the Bluetooth adapter. The app includes it only when the adapter already has that name. Test without the name field first, then repeat after a manual Bluetooth settings rename if the phone exposes that setting. Android manages the local BLE address. Public app APIs supply neither an arbitrary per-advertisement local name nor a chosen transmitter MAC. [Android AdvertiseData.Builder](https://developer.android.com/reference/android/bluetooth/le/AdvertiseData.Builder) · [Android BluetoothAdapter](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter)
- Android's legacy advertising API allows 31 bytes for advertising data and a separate 31-byte scan response. Typical flags, 16-bit service list and manufacturer data use 14 bytes. The 9-byte name needs 11 bytes with its AD header. The service UUID list and manufacturer-specific data use distinct API calls. The reference has no Service Data AD field. Android controls the generated flags, advertising interval and address behavior. It does not expose Zwahoo's preferred connection parameter in the legacy advertising builder. [Android BluetoothLeAdvertiser](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser) · [Android AdvertiseSettings.Builder](https://developer.android.com/reference/android/bluetooth/le/AdvertiseSettings.Builder)

## GATT profile and initial exchange

All three characteristic UUIDs below have the suffix `-19ca-4651-86e5-fa29dcdd09d1`. Version 0.1.1 follows the assignments from the physical Ride capture. [Ride capture](https://www.makinolo.com/blog/2024/07/26/zwift-ride-protocol/) · [Characteristic assignments](https://www.makinolo.com/blog/2023/10/08/connecting-to-zwift-play-controllers/#race-controller-service)

| UUID prefix or descriptor | Properties | Android attribute permissions |
| --- | --- | --- |
| `00000002` | Notify | No direct characteristic reads or writes |
| `00000003` | Write, Write Without Response | Write |
| `00000004` | Indicate | No direct characteristic reads or writes |
| `0x2902` on `02` and `04` | Client Characteristic Configuration | Read and Write |

The app opens a GATT server and waits for the successful service-registration callback before asking Android to advertise. On connection, the app keeps each central's subscription values independently. A write of `01 00` to the CCCD on `02` enables notifications, a write of `02 00` to the CCCD on `04` enables indications, and `00 00` disables the respective subscription. The initial exchange answers a write beginning with ASCII `RideOn` (`52 69 64 65 4F 6E`) on `03` with those same six bytes as an indication on `04` after that central subscribes. The app logs the Android send result and completion callback. An indication is requested with confirmation and Android 13+ uses the API taking a payload directly. [Ride handshake](https://www.makinolo.com/blog/2024/07/26/zwift-ride-protocol/#the-protocol) · [Android BluetoothGattServer](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer)

Makinolo's capture of a physical **Ride** retains the characteristic assignments documented for Play (`02` notify, `03` write, `04` indicate) and describes a plain `RideOn` exchange. BikeControl's Click V2 uses the `02 03` start-frame suffix, and its split-side implementations send that frame. The original Click parser uses `01 03` for the start response and `0x37` for button messages. The Android implementation takes its initial reply from Zwahoo. [Makinolo Ride capture](https://www.makinolo.com/blog/2024/07/26/zwift-ride-protocol/) · [Makinolo characteristic assignments](https://www.makinolo.com/blog/2023/10/08/connecting-to-zwift-play-controllers/#race-controller-service) · [BikeControl Click V2 left-side handshake](https://github.com/OpenBikeControl/bikecontrol/blob/e91f70131edccff41f13ab2f9beec64c2e37e6cb/lib/bluetooth/devices/zwift/zwift_clickv2_left_side.dart#L77-L85) · [BikeControl original Click](https://github.com/OpenBikeControl/bikecontrol/blob/e91f70131edccff41f13ab2f9beec64c2e37e6cb/lib/bluetooth/devices/zwift/zwift_click.dart)

## Hardware test results

With `Zwift SF2` in the scan response, Zwift listed version 0.1.0 as `Zwift Ride 4242` and the phone recorded a successful GATT connection. The Android log showed requests to enable indications on `03` (`02 00`) and notifications on `04` (`01 00`). After a minute, the log still showed no characteristic write or `RideOn` response. The log records the descriptor requests upon receipt. The next action by Zwift is unknown.

Version 0.1.1 changed the characteristic layout while retaining the advertisement and six-byte Ride response. In the retest, the rider reported successful pairing. The phone logged a successful `RideOn` indication completion (`status=0`) and received repeated writes to `00000003-19ca-4651-86e5-fa29dcdd09d1`. The visible payloads, in order, were `00 08 00`, `00 08 10`, `00 08 8A 06`, and `00 08 83 06`.

In the published Ride capture, `00 08 00` elicited a controller-information indication. The meanings and required replies for the other three variants in the Android log are unverified. Version 0.1.1 logs these commands and the only application-level reply it sends is the initial `RideOn` indication. [Ride control-point commands](https://www.makinolo.com/blog/2024/07/26/zwift-ride-protocol/#control-point-commands)

## Stage 2 button messages

Stage 2 sends message type `0x23` followed by Protobuf field 1 (tag `08`, unsigned varint), with a 32-bit active-low button bitmap. The rider reported that neither gear button triggered the Zwift tutorial in 0.2.0. Android reported successful sends for press and release. The 0.2.0 masks `0x2000` and `0x0400` correspond to RS2 and the left auxiliary button in the current Ride references. [RideToWoosh's physical controller decoder](https://github.com/TheInGoF/RideToWoosh/blob/547ad29c1b59f62c5f2d77970da037573e434c43/RideToWooshHID.ino#L75-L94) · [Game Controller for Zwift button reference](https://github.com/VoltageSolutions/GameControllerForZwift/blob/5d2abcbe16cced971fdb1ccde7e8f9a68d6398ff/docs/how-it-works/button-reference.md#L13-L44)

Version 0.2.2 exposes each Ride shifter separately. The primary buttons are **RS1 · Gear Up** and **LS1 · Gear Down**. Each test button clears its own bit, including the left auxiliary bit that was used for Gear Down in 0.2.0. Setting all bits gives the released state. The digital-only Stage 2 frame carries field 1 and fits the default BLE ATT MTU. [BikeControl's action mapping](https://github.com/OpenBikeControl/bikecontrol/blob/e91f70131edccff41f13ab2f9beec64c2e37e6cb/lib/bluetooth/devices/zwift/ride_controller_press.dart#L33-L38) · [BikeControl's masks](https://github.com/OpenBikeControl/bikecontrol/blob/e91f70131edccff41f13ab2f9beec64c2e37e6cb/lib/bluetooth/devices/zwift/zwift_ride.dart#L326-L349)

| State | Button mask | Notification payload on `02` |
| --- | --- | --- |
| All buttons released | `0x0000` | `23 08 FF FF FF FF 0F` |
| LS1 pressed | `0x0100` | `23 08 FF FD FF FF 0F` |
| LS2 pressed | `0x0200` | `23 08 FF FB FF FF 0F` |
| RS1 pressed | `0x1000` | `23 08 FF DF FF FF 0F` |
| RS2 pressed | `0x2000` | `23 08 FF BF FF FF 0F` |
| Left Aux pressed | `0x0400` | `23 08 FF F7 FF FF 0F` |

A client is ready after it subscribes to notifications on `02` and Android reports the `RideOn` indication on `04` completed. The app sends a baseline released frame when the client becomes ready. Each tap produces a press and then a release at least 100 ms after Android reports the press sent. This interval is a Stage 2 test choice. Indications and notifications share a queue that waits for Android's `onNotificationSent` callback between sends. [Android GATT server callback](https://developer.android.com/reference/android/bluetooth/BluetoothGattServerCallback#onNotificationSent(android.bluetooth.BluetoothDevice,int))

## Click plus and minus tutorial test

The rider reported that none of the Ride test buttons in 0.2.2 satisfied the tutorial's `+` prompt. The existing advertisement uses the device type `0x09`, which jat255 identifies as the original Click (BC1). The displayed name in Zwift is `Zwift Ride 4242`. The controller type Zwift uses for tutorial input remains unverified. [Click device type](https://github.com/jat255/zwift_click_handling/blob/7cf896da3785d2971f5c7b489aeb810404d65cec/constants.py#L7-L28)

Version 0.2.3 adds separate buttons that send Click V1 frames over the already paired `FC82` service on characteristic `02`. The physical Click reference observed two varint fields, field 1 for plus and field 2 for minus. Zero denotes a press and one denotes release. The rider confirmed that the tutorial recognized both buttons with the existing advertisement and initial handshake. This establishes acceptance of the Click frames in the tutorial on the tested setup. [Physical Click input observations](https://github.com/jat255/zwift_click_handling/blob/7cf896da3785d2971f5c7b489aeb810404d65cec/app.py#L113-L144) · [BikeControl Click frame encoder](https://github.com/OpenBikeControl/bikecontrol/blob/e91f70131edccff41f13ab2f9beec64c2e37e6cb/lib/bluetooth/emulation/emulated_peripherals.dart#L299-L308)

| Click state | Notification payload on `02` |
| --- | --- |
| Plus pressed | `37 08 00 10 01` |
| Minus pressed | `37 08 01 10 00` |
| Both released | `37 08 01 10 01` |

## Android checks and open questions

The app checks the advertised BLE system feature and obtains a `BluetoothLeAdvertiser` with Bluetooth on. GATT server creation, service registration and the advertising callback supply the actual startup result. Phone firmware can still affect visibility and connection behavior. Android 12 and above requires runtime `BLUETOOTH_ADVERTISE` and `BLUETOOTH_CONNECT`. Older versions use the manifest Bluetooth permissions. The phone operates as a peripheral, so the app requests neither scan nor location permission. The app closes its advertiser and GATT server when stopped and uses a local 12-second startup timeout for missing Android callbacks. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) · [Android BluetoothManager](https://developer.android.com/reference/android/bluetooth/BluetoothManager)

Discovery, pairing and post-handshake writes were observed with version 0.1.1 on the tested setup, and the tutorial recognized both Click buttons in 0.2.3. The minimum discovery filter, short-address handling and actual shifts during a ride remain open. [Run the hardware test](testing.md)
